A1. "Admin por variável de ambiente e o resto no banco: o que acha?"
  Boa ideia, com 3 ajustes. Hoje o backend já faz algo parecido, mas de um jeito
  que tem falha reproduzida (testei):
   - Se alguém se registra em /auth/register com o MESMO e-mail do admin ANTES do
     primeiro login do admin, a conta fica de role "user". O login com a senha do
     .env passa a entrar como "user" (o admin real fica sem painel) e a senha do
     invasor também funciona. Ou seja, o admin pode ser trancado para fora.
   - A senha do .env é comparada no meio do login (não em tempo constante) e o
     usuário admin é criado DENTRO do login.
   - O frontend tem um segundo caminho de login de admin (contingência) que não
     passa pelo banco.
  Desenho recomendado:
   1. Variáveis ADMIN_EMAIL e ADMIN_PASSWORD (mínimo 12 caracteres; recusar
      "admin123" e similares).
   2. Na INICIALIZAÇÃO do backend (lifespan), um "upsert": cria ou atualiza a
      linha do admin no banco (role admin, senha com bcrypt, ativo). Se já
      existir um usuário comum com esse e-mail, ele é promovido e a senha é
      sobrescrita pela do .env. Isso neutraliza o pré-cadastro.
   3. O login SEMPRE confere só contra o hash do banco. Nenhuma comparação com
      variável de ambiente no login, nenhuma lógica de admin no frontend.
   4. Trocar a senha = mudar a variável e reiniciar.
  Por que o admin precisa existir como LINHA no banco: tabelas guardam
  reviewed_by/admin_id apontando para users (auditoria). Sem a linha, a
  auditoria quebra.
  Snippet:
      async def ensure_admin(db):
          email = settings.ADMIN_EMAIL.strip().lower()
          pwd = settings.ADMIN_PASSWORD
          if not email or not pwd:
              return
          if len(pwd) < 12 or pwd.lower() in {"admin123","senha123","password"}:
              raise RuntimeError("ADMIN_PASSWORD fraca")
          u = (await db.execute(select(User).where(func.lower(User.email) == email))).scalar_one_or_none()
          h = get_password_hash(pwd)
          if u is None:
              db.add(User(email=email, name="Administrador", role="admin",
                          password_hash=h, is_active=True))
          else:
              u.role, u.password_hash, u.is_active = "admin", h, True
          await db.commit()

A2. "O projeto está complexo demais?"
  Sim, e os números mostram: 20 migrations, 29 tabelas, a tabela businesses com
  50 colunas, 3 formas de identidade (admin, owner por OTP, user por registro),
  4 mecanismos de esquema (migrations SQL, reset_all.sql, runner migrate.py e uma
  pasta alembic sem versões) e módulos que não fazem parte da ideia original
  (planos/pagamentos, bot de leads no WhatsApp, rede de indicações, lista de
  espera por cidade). A ideia original (vitrine + vagas) cabe em umas 12 tabelas.
  A PARTE C propõe congelar o que não é núcleo (sem apagar dados) e simplificar o
  cadastro.

A3. "Por que login e criar empresa dão tanto trabalho?" (causa raiz)
  1. Criar empresa e ter conta são coisas SEPARADAS. A candidatura é anônima: o
     negócio nasce com owner_user_id = NULL (confirmei no banco). Para entrar, o
     empresário precisa depois "reivindicar" pelo código do WhatsApp.
  2. Esse código depende de um provedor de WhatsApp (Evolution/Meta). Sem as
     credenciais, o sistema cai no provedor "Console", que só escreve no log:
     ninguém recebe nada e ninguém consegue entrar.
  3. O código OTP e os limites ficam na MEMÓRIA do processo (dicionário em
     otp.py): somem a cada reinício e quebram com mais de 1 worker.
  4. O dono "reivindicado" vira um usuário sintético
     (owner-xxxx@patriotaindica.internal) sem e-mail real nem senha: não há
     recuperação de acesso nem aviso por e-mail.
  5. Existe /auth/register, que cria um usuário "user" sem nenhuma função no
     sistema (não consegue criar nem possuir empresa).
  6. O frontend MASCARA falhas: se o backend estiver fora do ar, a rota
     /api/v1/businesses/application responde 201 "Candidatura recebida" com id
     falso (app-local-...) e NÃO grava nada. O login também tem um modo de
     contingência. Parece que funciona, mas nada foi salvo.
  7. Se a lista de categorias da API falhar, o formulário usa 28 categorias de
     exemplo com ids falsos (c1..c28) e envia o nome como "nicho proposto",
     poluindo as categorias com duplicatas.
  8. A migration 018 falha num PostgreSQL real (ver D1): quem usa o runner oficial
     fica sem as tabelas de vagas e sem as migrations 019 e 020.

B1. ONDE CADA INFORMAÇÃO É GUARDADA
  Banco (PostgreSQL)  : usuários, empresas, categorias, cidades, vagas, planos,
                        assinaturas, pagamentos, leads, consentimentos,
                        denúncias, logs de auditoria, eventos de clique.
  Redis               : limites de requisição e tokens de refresh (sessão).
  MEMÓRIA do backend  : códigos OTP e limites do OTP (otp.py)  <- risco (A3.3)
  Disco do container  : imagens enviadas em /static/uploads. O docker-compose
                        NÃO tem volume para isso: as imagens somem a cada
                        deploy/recriação do container.
  Navegador           : cookie/sessão de login, cópia local das categorias
                        (localStorage guia_local_categories, que fica velha) e
                        dados de apresentação da sessão do admin (sessionStorage).
  Logs                : mensagens de erro/diagnóstico (conferir se não há PII).

B2. MAPA DE ENTIDADES E RELAÇÕES (como está hoje)
  users (admin | owner | user)
    1 --- N businesses            (businesses.owner_user_id, ON DELETE SET NULL)
    1 --- N subscriptions         (owner_user_id, CASCADE)
    1 --- N payments              (user_id, CASCADE)
    1 --- N consents, referrals, invitations, reports(resolved_by) ...
  businesses (vitrine)
    N --- N categories            via business_categories (CASCADE/RESTRICT)
    1 --- N job_openings          (CASCADE)  -> job_reports, job_review_log
    1 --- N business_review_log   (CASCADE)  <- apaga a auditoria junto
    1 --- N business_pending_changes, contact_events, invitations, reports,
            consents, lead_offers, lead_reviews, peer_endorsements, referrals
    N --- 1 cities?               NÃO há FK: businesses.city/state são TEXTO LIVRE
  plans 1 --- N subscriptions / payments (sem ON DELETE: NO ACTION)
  leads 1 --- N lead_offers / lead_reviews (CASCADE)
  Observação: as relações centrais (user -> business -> categorias/vagas) estão
  corretas. Os problemas estão nas bordas (integridade, exclusão, texto livre).

B3. ACHADOS (severidade: C crítico, A alto, M médio, B baixo)

[D1] (C) Migration 018 não executa num PostgreSQL real
  Erro: "functions in index expression must be marked IMMUTABLE" no índice
  uq_job_report_daily (usa created_at::date, que depende do fuso).
  Efeito: o runner oficial (migrate.py) executa cada arquivo como uma unidade e
  PARA no erro: as tabelas job_* não são criadas e as migrations 019 e 020 ficam
  sem aplicar. Já pelo caminho do Docker (psql em docker-entrypoint-initdb.d) o
  restante da 018 passa e só o índice de deduplicação de denúncias fica faltando.
  Dois caminhos, dois resultados diferentes. A busca da home tolera a ausência
  das vagas (registra "Falha ao buscar vagas" e segue), mas o módulo de vagas
  não funciona.
  Correção: editar a 018 trocando o índice por
      CREATE UNIQUE INDEX uq_job_report_daily
        ON job_reports (job_id, ip_hash, ((created_at AT TIME ZONE 'UTC')::date));
  (a 018 nunca foi aplicada com sucesso pelo runner, então pode ser editada no
  repositório; manter também um CREATE ... IF NOT EXISTS na 021 para bancos
  criados via Docker). Adicionar ao CI um teste que sobe PostgreSQL+PostGIS e
  aplica TODAS as migrations do zero.

[D2] (A) Dois sistemas de migração concorrentes + script de reset perigoso
  - Docker aplica migrations só na PRIMEIRA criação do banco (initdb), com psql
    que continua após erros; migrate.py aplica com controle de versão e para no
    erro; database/scripts/reset_all.sql (gerado) faz DROP SCHEMA e registra tudo
    como 'manual_reset' (checksum falso, que explica o teste de drift falhando);
    existe ainda uma pasta alembic sem nenhuma versão.
  - migrate.py lê DATABASE_URL só de backend/.env e ignora a variável de
    ambiente (no Docker/Easypanel ele não acha o banco, a menos que use
    --database-url).
  Correção: UM único caminho. Serviço "migrate" de execução única no compose
  (roda migrate.py com a URL do ambiente e termina) antes do backend; remover
  alembic/ e o uso de initdb para migrations; mover reset_all.sql para
  scripts/dev (sem estar no pacote de produção) com confirmação interativa.

[D3] (A) Colunas NOT NULL no ORM aceitam NULL no banco (órfãos possíveis)
  business_review_log.business_id, contact_events.business_id,
  invitations.business_id, lead_offers.lead_id/business_id,
  lead_reviews.lead_id/business_id, leads.urgency, payments.user_id/plan_id,
  referrals.referred_business_id, reports.business_id,
  subscriptions.owner_user_id/plan_id, wa_optins.origin.
  Inverso: subscriptions.current_period_start é NOT NULL no banco e opcional no
  ORM. Coluna só no banco: contact_events.job_id (sem campo no modelo).
  Correção: decidir para cada uma (obrigatória ou opcional), limpar órfãos
  (backup antes), aplicar NOT NULL e alinhar o ORM (migration 021, abaixo).

[D4] (A) Política de exclusão apaga auditoria e histórico financeiro
  - business_review_log e job_review_log: ON DELETE CASCADE. Apagar uma empresa
    apaga a trilha de decisões (o oposto de auditoria).
  - payments.user_id e subscriptions.owner_user_id: CASCADE. Apagar o usuário
    apaga o histórico financeiro (há obrigação de guarda fiscal).
  - businesses.owner_user_id: SET NULL. Apagar o usuário deixa empresas públicas
    sem dono.
  Correção: nunca apagar de verdade. Exclusão lógica (deleted_at) + anonimização
  (D5); FKs de auditoria e financeiro como RESTRICT.

[D5] (A) Direito de exclusão (LGPD) não é executado
  O canal do titular registra o pedido (tabela data_subject_requests), mas o
  código só atualiza consentimentos: nenhum dado de empresa/usuário é anonimizado
  ou removido. Pedido de exclusão fica "pendente" para sempre.
  Correção: função de anonimização (nome/e-mail/telefone/CPF/descrição/logos
  viram valores neutros, empresa sai da vitrine, vagas encerradas, consentimentos
  revogados, histórico financeiro e auditoria preservados sem dado pessoal) e
  endpoint/ação do admin para executá-la, registrando no log.

[D6] (M) Status e papéis como texto livre (14 colunas sem CHECK/enum)
  users.role, subscriptions.status, payments.status, leads.status,
  lead_offers.status, lead_reviews.status, referrals.status, reports.status,
  categories.status, cities.status, wa_optins.status,
  data_subject_requests.status, business_pending_changes.status e
  contact_events.event_type aceitam qualquer texto (um erro de digitação vira
  um papel/status inválido). Já businesses.status, listing_type, service_mode e
  source são ENUM, e job_openings tem CHECK: o padrão é misto.
  Correção: um padrão só (VARCHAR + CHECK é o mais simples de evoluir). Levantar
  os valores realmente usados no código antes de criar cada CHECK.

[D7] (M) Lacunas de unicidade
  - Nenhuma regra impede duas contas com e-mails que diferem só em maiúsculas
    (a aplicação normaliza, o banco não garante).
  - subscriptions: nada impede duas assinaturas ativas para o mesmo dono.
  - businesses: o documento (CNPJ/CPF) deixou de ser único (necessário para donos
    com várias empresas), e não há regra alternativa: o mesmo WhatsApp+nome pode
    ser cadastrado várias vezes.
  - referrals e consents sem unicidade por (indicada) e (empresa, tipo, versão).
  Correção: índices únicos parciais (migration 021).

[D8] (M) 21 chaves estrangeiras sem índice
  business_pending_changes(proposed_by_user_id, reviewed_by),
  business_review_log(admin_id), businesses(reviewed_by),
  categories(proposed_by_business_id), category_aliases(category_id),
  contact_events(job_id), invitations(created_by, used_by_user_id),
  job_openings(created_by), job_reports(job_id), lead_reviews(lead_id),
  leads(matched_business_id), payments(business_id, plan_id),
  referrals(referred_business_id, referred_user_id, referrer_business_id),
  reports(resolved_by), subscriptions(business_id, plan_id).
  Efeito: junções e CASCADE lentos conforme a base cresce.

[D9] (M) Cidade e telefone com mais de uma fonte de verdade
  - Existe a tabela cities (com slug e status), mas businesses.city/state são
    texto digitado e a busca filtra por ILIKE '%texto%': "Campinas", "campinas",
    "Campinas - SP" viram cidades diferentes, e "São Paulo" casa com qualquer
    nome que contenha "São Paulo".
  - Telefone: businesses.whatsapp (como digitado) e businesses.whatsapp_e164
    (normalizado), além de users.phone.
  Correção: businesses.city_id (FK para cities) preenchido por seleção na lista
  (nunca digitado); manter só o telefone normalizado em E.164 para lógica e o
  formatado só para exibição.

[D10] (M) Modelo de empresa largo demais (50 colunas) com estado espalhado
  O "estado" da empresa está em status + owner_paused + location_pending +
  document_flag_duplicate + is_verified + geocode_source + e na tabela
  business_pending_changes. Isso explica boa parte da dificuldade de entender o
  que aparece ou não na vitrine.
  Correção: documentar uma regra única de visibilidade ("aparece se
  status='approved' AND NOT owner_paused AND deleted_at IS NULL") e mover
  colunas de operação (geocode, flags de triagem) para uma tabela
  business_ops (1:1) quando sobrar tempo.

[D11] (M) Assinatura por usuário, não por empresa
  subscriptions.owner_user_id é obrigatória e business_id é opcional: não está
  claro se o plano vale para o dono (todas as empresas) ou para uma empresa. A
  busca já usa o plano da empresa (prioridade/selo). Definir e aplicar uma regra
  (recomendado: plano POR EMPRESA). Como monetização será congelada (Parte C), é
  só registrar a decisão.

[D12] (M) Documento pessoal em texto puro
  CPF/CNPJ ficam em businesses.document_number sem proteção. CPF é dado pessoal.
  Correção: manter só para o admin (já não sai na API pública), nunca em logs;
  avaliar criptografia de coluna (pgcrypto) ou guardar só o CNPJ e, para autônomo,
  os 3 últimos dígitos visíveis + hash.

[D13] (M) Imagens
  Sem volume no compose, as imagens se perdem; não há rotina de remoção de
  arquivos órfãos. Correção: volume nomeado montado em /app/static/uploads (ou
  S3/MinIO) + backup junto do banco.

[D14] (B) contact_events guarda user_agent e referrer como texto sem limite;
  não há coluna de IP (bom). Truncar na aplicação (255) e manter a retenção de
  90 dias. updated_at só é atualizado por trigger em businesses.

[D15] (B) Sementes (categorias 54, cidades 13, planos 3, termos 30) estão dentro
  das migrations. Funciona, mas mudar um preço exige nova migration (a 019 faz
  isso). Para o MVP basta; depois mover para script de seed idempotente.
