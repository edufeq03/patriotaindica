================================================================================
PATRIOTA INDICA - RELATORIO DE SEGURANCA + DESIGN DE NICHOS DINAMICOS
Auditoria do codigo enviado (patriotaindica-main.zip) e plano de implementacao
================================================================================

Como usar: cole este documento inteiro na outra IA de codigo. A secao 9 traz o
prompt final, em etapas. As secoes 3 a 5 sao a referencia tecnica.

--------------------------------------------------------------------------------
1. RESUMO EXECUTIVO
--------------------------------------------------------------------------------
O projeto tem uma boa base (bcrypt, SQL parametrizado, candidatura que nunca
publica direto, CPF/CNPJ fora da API publica, log de auditoria). Mas, no estado
atual, NAO PODE IR PARA PRODUCAO. Existem 4 problemas criticos que permitem
tomar o painel de triagem sem nenhuma vulnerabilidade "sofisticada":

  [C1] O backend sobe com um JWT_SECRET_KEY publico (esta no codigo) porque o
       docker-compose nao passa o segredo. Qualquer pessoa forja token de admin.
  [C2] Credencial padrao admin123 (seed + formulario de login ja preenchido).
  [C3] A aplicacao usa o superusuario "postgres" com senha "postgres": o RLS
       (migration 003) nao protege nada, porque superusuario ignora RLS.
  [C4] O frontend ainda e prototipo: admin, painel, convite, reivindicacao e
       /go usam mockData + localStorage/sessionStorage. O OTP e gerado e
       exibido no proprio navegador e aceita "123456". O login admin tem
       "modo sandbox" decidido no cliente.

Contagem: 4 criticos, 8 altos, 14 medios. Nichos dinamicos: SIM, e possivel
(secao 4) - com um desenho que evita spam, duplicatas e abuso.

IMPORTANTE sobre o estado do codigo: o backend ja tem busca, categorias
(somente leitura), empresas (perfil, candidatura, denuncia), /go, triagem e
auth. NAO existem no backend: painel do dono, reivindicacao/OTP, convites,
importacao CSV, cadastro assistido, upload de midia, criacao de categorias.
Ou seja: parte das protecoes abaixo precisa ser construida JUNTO com esses
endpoints, e nao depois.

--------------------------------------------------------------------------------
2. MODELO DE AMEACA (quem vai atacar e por que)
--------------------------------------------------------------------------------
a) Bots de spam: enchem formularios publicos (candidatura, denuncia, registro),
   inflam metricas de clique, raspam telefones/WhatsApp.
b) Concorrentes e oportunistas: denuncias em massa para derrubar rivais,
   cliques falsos, candidatura com dados de terceiros (usar CNPJ alheio).
c) Atacantes oportunistas: varrem a internet atras de segredo padrao, admin123,
   /docs aberto, banco exposto. Os criticos C1-C3 sao exatamente isso.
d) Donos de empresa maliciosos ou com conta sequestrada: depois de aprovados,
   trocam site/telefone por phishing sem passar de novo pela triagem.
e) Atencao hostil por causa do posicionamento da marca: um diretorio que se
   identifica por valores politicos/ideologicos tende a atrair DDoS,
   defacement, doxxing dos donos listados, denuncia coordenada e raspagem da
   lista de signatarios. Isso nao e juizo de valor: e o fator que eleva a
   probabilidade de ataque dirigido e deve entrar no planejamento (rate
   limit forte, WAF/Cloudflare, minimizar dados publicos, backups).
f) Falhas de privacidade (LGPD): vazamento de dados de MEIs (endereco
   residencial, CPF, telefone) gera responsabilidade juridica.

3. ACHADOS DE SEGURANCA (com local no codigo e correcao)
--------------------------------------------------------------------------------

############################  CRITICOS  ########################################

[C1] JWT secret padrao publico
  Onde: backend/app/core/config.py (default "change_this_to_a_very_secure...");
        docker-compose.yml (servico backend NAO define JWT_SECRET_KEY nem env_file).
  Impacto: o backend usa o valor padrao, que esta no repositorio. Com ele, um
        atacante assina um token com "sub" = UUID de um admin. Se o seed foi
        executado, o UUID do admin e fixo e publico
        (a0000000-0000-0000-0000-000000000001); mesmo sem seed, o UUID de
        admin vaza em respostas (admin_id em /triage/decision, logs).
        Resultado: aprovar/reprovar/suspender qualquer empresa.
  Correcao:
    - Remover o default: JWT_SECRET_KEY obrigatorio; a aplicacao NAO inicia se
      faltar, tiver menos de 32 bytes ou contiver "change_this".
    - Gerar com: openssl rand -hex 64. Injetar via secrets do Easypanel/env,
      nunca no repositorio. Rotacionar se ja foi usado em algum lugar.
    - Snippet (pydantic v2):
        from pydantic import field_validator
        class Settings(BaseSettings):
            JWT_SECRET_KEY: str            # sem default
            @field_validator("JWT_SECRET_KEY")
            @classmethod
            def strong_secret(cls, v):
                if len(v) < 32 or "change_this" in v.lower():
                    raise ValueError("JWT_SECRET_KEY fraco ou padrao")
                return v
    - Adicionar claims iss, aud, jti e validar iss/aud no decode.

[C2] Credenciais padrao
  Onde: database/seed/sample_businesses_campinas.sql (admin, senha demo
        admin123); frontend/src/app/admin/page.tsx (campos de login ja
        preenchidos com admin@patriotaindica.com.br / admin123 e mensagem de
        erro que repete a credencial).
  Correcao:
    - Nenhum usuario admin em seed. Criar o primeiro admin por script de uso
      unico (python -m backend.scripts.create_admin) com senha aleatoria
      impressa uma vez e troca obrigatoria no primeiro login.
    - Remover valores pre-preenchidos e qualquer texto com credencial.
    - Seeds de empresas fake (sample_businesses_campinas.sql) so em ambiente
      de desenvolvimento, nunca montados em producao.
    - 2FA TOTP obrigatorio para role admin (pyotp), com codigos de recuperacao.

[C3] Banco com superusuario e RLS inocuo
  Onde: docker-compose.yml (POSTGRES_USER/PASSWORD postgres/postgres,
        DATABASE_URL com postgres); migrations/003_rls_and_permissions.sql.
  Problemas:
    1) Superusuario ignora RLS. As politicas nao valem nada para o backend.
    2) As politicas leem current_setting('request.jwt.claim.*'), que o FastAPI
       NUNCA define (isso e convencao do Supabase/PostgREST).
    3) Senha trivial hardcoded no compose.
    4) Tabelas com RLS ligado e ZERO politicas (business_review_log,
       invitations): quebram assim que existir um role sem BYPASSRLS.
  Correcao:
    - Tres roles: migrator (DDL, so em deploy), app_rw (aplicacao, sem
      superuser, sem BYPASSRLS), readonly (relatorios/metricas).
        CREATE ROLE app_rw LOGIN PASSWORD '...' NOSUPERUSER NOBYPASSRLS;
        GRANT USAGE ON SCHEMA public TO app_rw;
        GRANT SELECT, INSERT, UPDATE ON businesses, categories, ... TO app_rw;
        REVOKE UPDATE, DELETE ON business_review_log FROM app_rw;  -- append-only
        ALTER ROLE app_rw SET statement_timeout = '5s';
        ALTER TABLE businesses FORCE ROW LEVEL SECURITY;  -- idem demais tabelas
    - Decidir o modelo de autorizacao: (a) autorizacao na aplicacao + RLS como
      segunda camada, definindo por transacao
        SET LOCAL app.user_id = '<uuid>'; SET LOCAL app.role = '<role>';
      e reescrevendo as politicas para current_setting('app.user_id', true).
    - Senhas fortes e distintas por role, vindas de secrets. Postgres NUNCA
      publicado na internet (o compose atual nao publica a porta: manter assim;
      o README diz o contrario, corrigir o README).
    - Escrever teste que conecta como app_rw e prova que RLS bloqueia leitura
      de empresa nao aprovada e escrita em campo privilegiado.

[C4] Frontend e prototipo, com "seguranca" feita no navegador
  Onde: frontend/src/app/admin/page.tsx (sessao admin em sessionStorage,
        confiada via JSON.parse; fallback "sandbox" quando a API cai, com
        token fixo 'demo-local-jwt-sandbox-token'); components/
        BusinessProfileView.tsx (OTP gerado e MOSTRADO na tela; aceita
        '123456' como codigo universal); app/go/[type]/[id]/route.ts (usa
        mockData e console.log: nenhum clique chega ao banco);
        app/painel-empresa, app/convite/[token], categorias em localStorage
        ('guia_local_categories').
  Impacto: qualquer visitante abre a UI de admin (basta gravar a chave no
        sessionStorage ou derrubar a API); qualquer um "reivindica" qualquer
        perfil; metricas e categorias nao existem de verdade.
        Alem disso NEXT_PUBLIC_API_URL=/api/v1 no compose, mas o next.config.ts
        nao tem rewrites: a API nao e alcancavel pelo frontend.
  Correcao:
    - Remover TODO modo sandbox/mock do build de producao (mockData so atras de
      NODE_ENV !== 'production', idealmente fora do bundle).
    - Integrar o frontend aos endpoints reais; o Next.js passa a ser o unico
      ponto publico, com rewrites/BFF para o backend (backend nao exposto).
    - Gate de /admin e /painel-empresa no servidor (middleware.ts validando a
      sessao), nunca no cliente.
    - OTP 100% no servidor: gerar com secrets.randbelow, guardar apenas o HASH
      (SHA-256 + sal) no Redis com TTL de 5 min, maximo 5 tentativas, bloqueio
      por numero/IP, 3 envios por hora por numero; envio via WhatsApp Cloud API.
      Nenhum codigo fixo, nenhum codigo devolvido na resposta da API.

###############################  ALTOS  ########################################

[H1] Nenhum rate limiting (Redis existe mas nao e usado)
  Onde: config.py declara REDIS_URL; nenhum modulo usa Redis.
  Impacto: forca bruta em /auth/login; flood em /auth/register,
        /businesses/application, /report; escrita no banco por qualquer GET em
        /go; consultas pesadas em /search.
  Correcao: limitador por IP e por rota (Redis, janela deslizante), com IP real
        (uvicorn --proxy-headers --forwarded-allow-ips para o proxy). Limites
        sugeridos: login 5/min/IP e 10/hora/e-mail com bloqueio progressivo;
        register 3/hora/IP; application 3/dia/IP; report 5/dia/IP; /go
        30/min/IP; search 60/min/IP. Cloudflare (WAF + bot fight) na frente.
        Snippet minimo:
          async def rate_limit(r, key, limit, window):
              n = await r.incr(key)
              if n == 1: await r.expire(key, window)
              if n > limit: raise HTTPException(429, "Muitas requisicoes")

[H2] Formularios publicos sem protecao anti-bot e sem limites de tamanho
  Onde: POST /businesses/application, POST /businesses/{id}/report (os campos
        reason, details, contact_email sao parametros de QUERY STRING: ficam em
        logs de proxy, sem limite de tamanho), POST /auth/register.
  Correcao: corpo JSON com schema e max_length; captcha (Cloudflare Turnstile
        ou hCaptcha) em candidatura/denuncia/registro; deduplicar denuncia por
        (IP, empresa, 24h); denuncia NUNCA suspende automaticamente (so alerta
        o admin, para nao virar arma contra concorrentes); honeypot field.

[H3] Pos-aprovacao, o dono pode trocar dados de risco sem nova triagem
  Onde: migrations/003 (gatilho de reanalise).
  Problemas:
    1) O gatilho cobre nome, documento, whatsapp, endereco e location, mas NAO
       cobre website, phone, instagram, description, logo_url, banner_url,
       listing_type, service_mode/radius nem categorias. Um dono (ou conta
       sequestrada) troca o website por phishing e o /go/website redireciona
       todo o trafego.
    2) A politica p_businesses_owner_update so tem USING (sem WITH CHECK) e nao
       restringe colunas: o dono poderia gravar status='approved',
       is_verified=true ou trocar owner_user_id.
    3) O gatilho reverte para pending_review ate quando o ADMIN edita (o
       comentario diz o contrario).
  Correcao (recomendada): tabela business_pending_changes. O dono nunca edita
        a linha publicada; propoe mudancas, a versao APROVADA continua no ar,
        e campos de risco so entram apos aprovacao do admin (campos de baixo
        risco, como horario, aplicam direto). Alem disso:
    - Schema Pydantic separado para edicao do dono, extra="forbid", com
      allowlist explicita de campos (nunca expor status, is_verified,
      owner_user_id, document_*).
    - Trigger/privilegio de coluna impedindo nao-admin de alterar status,
      is_verified, owner_user_id, reviewed_*.

[H4] Localizacao definida pelo cliente
  Onde: businesses.py (application): latitude/longitude vem do corpo; se
        ausentes, cai silenciosamente em Campinas (-22.9056, -47.0608).
  Impacto: empresa fantasma posicionada em qualquer lugar; todas as candidaturas
        sem coordenada viram "centro de Campinas"; burla o escopo por cidade.
  Correcao: ignorar lat/lng do cliente. Geocodificar no servidor (CEP/endereco)
        com cache em Redis; gravar geocode_source e geocode_confidence; exigir
        que o ponto caia na cidade/UF declarada; admin confere no mapa. Se o
        geocode falhar, o registro vai para triagem manual, nunca para um
        ponto padrao.

[H5] Redirecionamento para URL arbitraria (phishing/malware)
  Onde: redirects.py (/go/website): so prefixa https:// se faltar; nenhuma
        validacao de host. Candidatura aceita website sem validacao.
  Correcao: validar com HttpUrl; permitir apenas http/https; bloquear IP
        literal, localhost, credenciais na URL (user:pass@), portas estranhas;
        checar Google Safe Browsing na aprovacao e a cada 30 dias; re-checar a
        cada mudanca (ver H3); opcional: pagina intermediaria "voce esta
        saindo do Patriota Indica". Em todo link externo: rel="nofollow
        noopener noreferrer ugc".

[H6] WhatsApp/telefone expostos em massa na API publica
  Onde: schemas BusinessPublicCard/BusinessDetail; search.py devolve
        "whatsapp" e "phone" em cada card; /businesses/by-slug tambem.
  Impacto: raspagem em massa para spam; o redirect /go (que mede cliques) pode
        ser contornado lendo o numero direto do JSON; para um site com
        marca ideologica, a lista de donos+telefones vira alvo de assedio.
  Correcao: remover whatsapp/phone dos cards e da listagem; entregar so via
        /go com rate limit, ou na pagina do perfil com carregamento sob
        interacao (clique). Paginacao com teto (page<=50) e limite por IP para
        dificultar scraping. CPF/CNPJ continuam privados (ja estao).

[H7] Configuracao insegura de producao
  Onde: config.py (DEBUG=True por padrao => engine echo=True registra SQL com
        PARAMETROS: e-mails, hashes de senha, telefones nos logs); main.py
        (/docs, /redoc e /openapi.json publicos); ENVIRONMENT sem efeito real.
  Correcao: DEBUG=False por padrao; em production desativar docs/openapi
        (docs_url=None, redoc_url=None, openapi_url=None); handler global de
        excecao retornando mensagem generica (sem stack); logs estruturados SEM
        PII; nivel INFO.

[H8] Enumeracao de usuarios e role autoatribuivel
  Onde: auth.py. /register responde "ja existe conta com este e-mail" (revela
        e-mails cadastrados); no login, usuario inexistente nao executa bcrypt
        (diferenca de tempo revela se o e-mail existe); register aceita
        role="owner" escolhido pelo proprio usuario.
  Correcao: /register com resposta generica + confirmacao por e-mail; executar
        verify_password contra um hash dummy quando o usuario nao existe;
        remover "role" do payload publico - "owner" deve derivar de
        businesses.owner_user_id depois de claim aprovado; senha com
        verificacao de senhas vazadas (HIBP k-anonymity) alem de min. 12
        caracteres; invalidar sessoes na troca de senha.

##############################  MEDIOS  ########################################

[M1] CORS permissivo: docker-compose define CORS_ORIGINS=["*"] com
     allow_credentials=True e methods/headers "*". Restringir as origens
     reais (https://seudominio), metodos e headers necessarios. Em producao
     nao ha motivo para "*".

[M2] Sessao/JWT: HS256, 24h, sem refresh/revogacao, guardado em sessionStorage
     (roubavel por XSS). Usar access de 15 min + refresh rotativo em cookie
     HttpOnly+Secure+SameSite=Strict (BFF no Next), lista de revogacao em
     Redis, logout real, sessao admin mais curta e com TOTP. Se algum dia usar
     cookie de sessao, adicionar protecao CSRF.

[M3] Validacao de entrada fraca (Pydantic): service_mode, listing_type,
     document_type, state, action da triagem sao str livres (valor invalido
     vira erro 500 do enum do Postgres); category_ids sem limite de tamanho e
     sem checar existencia (FK => 500); CNPJ/CPF sem digito verificador;
     website/instagram/telefone sem formato. Usar Literal/Enum, max_length em
     listas (max 3 categorias), validadores de CNPJ/CPF, HttpUrl, regex de
     Instagram ^[A-Za-z0-9._]{1,30}$, telefone E.164, model_config
     extra="forbid" em todos os schemas de entrada. Traduzir erros de banco
     (IntegrityError) para 4xx amigaveis.

[M4] Busca sem tetos: q sem tamanho maximo (trigram/tsquery pesado), radius_km
     sem limite (varredura global), lat/lng sem faixa valida (erro 500 em
     geography), paginacao funda com OFFSET. Limitar q<=80, radius<=100, lat
     [-90,90], lng [-180,180], page<=50; cache Redis de buscas populares;
     statement_timeout no role. Tambem testar: a query usa
     ":filter_type::listing_type" dentro de text(); o SQLAlchemy pode
     interpretar mal "::" colado a um parametro. Usar CAST(:filter_type AS
     listing_type) e cobrir com teste de integracao.

[M5] /go via GET com efeito colateral: robos, previews de link (WhatsApp,
     Facebook) e qualquer <img src="/go/..."> de terceiros inflam metricas e
     enchem a tabela; referrer/user_agent sao TEXT sem limite. Filtrar bots por
     User-Agent, nao registrar HEAD/prefetch, dedupe (hash(ip+ua)+empresa+
     dia), truncar campos (referrer 255, ua 255), guardar IP somente como hash
     com sal rotativo, retencao de 90 dias com agregacao diaria. Ideal:
     registrar via POST/beacon disparado pelo clique real.

[M6] Slug: loop sem limite, com condicao de corrida (dois cadastros iguais =>
     violacao de UNIQUE => 500); nomes so com simbolos geram slug vazio.
     Gerar slug com sufixo curto aleatorio, tratar IntegrityError com retry
     limitado, reservar palavras (admin, api, go, convite, painel-empresa).

[M7] Triagem sem regras: /triage/decision permite aprovar sem checklist
     (CNPJ inativo, WhatsApp nao verificado), reaprovar rejeitada, etc.;
     reviewed_by nunca e preenchido (so reviewed_at). GET /triage/checklist
     escreve no banco e chama API externa sem cache/limite. Criar maquina de
     estados valida; approve exige whatsapp_verified_at, cnpj_situation ATIVA
     (ou override com justificativa gravada), geocode ok e niche resolvido;
     preencher reviewed_by; checklist como POST com cache de 24h; log de
     auditoria append-only; opcional: duas pessoas para o selo "Verificada".

[M8] Container/dependencias: imagens rodam como root; sem limites de CPU/RAM;
     backend sem healthcheck; requirements com ">=" (nao reprodutivel, sem
     lock/hash); python-jose tem historico de CVEs e pouca manutencao
     (trocar por PyJWT); passlib sem manutencao e nao e usado (remover);
     psycopg2-binary desnecessario com asyncpg. Criar usuario nao-root no
     Dockerfile, pin de versoes + hashes (pip-compile --generate-hashes),
     pip-audit, npm audit, Dependabot, Trivy no CI.

[M9] Sem cabecalhos de seguranca (nem no Next, nem no backend): CSP,
     Strict-Transport-Security, X-Content-Type-Options, frame-ancestors/
     X-Frame-Options, Referrer-Policy, Permissions-Policy (geolocation=(self)).
     Configurar em next.config.ts (headers()) e no proxy. TrustedHostMiddleware
     no FastAPI.

[M10] Midia: logo_url/banner_url aceitam URL externa arbitraria (rastreia
      visitantes, conteudo improprio, mixed content). Upload proprio com:
      validacao por magic bytes (nao so extensao), 2 MB, reencode com Pillow
      (remove EXIF e payloads), nome aleatorio, dominio/bucket separado,
      sem SVG enviado por usuario, antivirus opcional (ClamAV).

[M11] LGPD e juridico: Termos e Privacidade sao links para "/" (placeholders);
      nao ha registro de consentimento, retencao, canal do titular nem
      encarregado (DPO). Enderecos de MEI sao dados pessoais (show_full_address
      false por padrao: manter). ATENCAO: a "Carta de Principios" inclui
      valores de natureza religiosa/politica; a adesao vinculada a pessoa
      identificavel (MEI/autonomo) pode configurar dado pessoal SENSIVEL
      (LGPD art. 5, II), exigindo consentimento especifico e destacado,
      finalidade clara, revogacao facil e exclusao do perfil. A frase do README
      "nao armazenamos filiacao partidaria" nao basta se a adesao em si revela
      conviccao. Procurar parecer de advogado de protecao de dados ANTES do
      lancamento.

[M12] Convites (a construir): token VARCHAR(64) sem regra de geracao. Gerar com
      secrets.token_urlsafe(32); guardar apenas o hash SHA-256; uso unico;
      expiracao curta (7 dias); vinculado ao telefone; rate limit em
      /convite/[token] (enumeracao); invalidar ao usar.

[M13] Cadastro assistido e CSV (a construir): CSV e vetor de injecao de formula
      (=, +, -, @ no inicio de celula) e de arquivo gigante. Limite de 2 MB e
      2000 linhas, parse em streaming, validacao por linha com o MESMO schema
      da candidatura, neutralizar celulas que iniciam com = + - @ ao exportar,
      relatorio de erros por linha, tudo entra como pending_review.

[M14] Infra e operacao (Contabo + Easypanel): firewall (ufw) liberando apenas
      80/443 e SSH por chave em porta nao padrao; fail2ban; desativar login
      SSH por senha/root; atualizacoes automaticas de seguranca; Postgres e
      Redis SOMENTE na rede interna do Docker, Redis com senha; backup diario
      criptografado do Postgres (pg_dump -> storage externo) com teste de
      restauracao mensal; monitoramento (uptime + alertas de erro 5xx);
      Cloudflare na frente (DNS proxied, WAF, rate limiting, modo "under
      attack" de emergencia); logs sem PII com retencao definida.

--------------------------------------------------------------------------------
4. NICHOS DINAMICOS - "Cuidador de Iguanas Selvagens"
--------------------------------------------------------------------------------
4.1 E possivel?
SIM. O fluxo que voce descreveu (o primeiro cria, o proximo seleciona) funciona
e e uma boa ideia para cauda longa. O risco de deixar 100% aberto (criar e
publicar na hora) e real:
  - spam e nomes ofensivos/golpistas virando pagina publica indexada no Google
    (cada categoria gera /cidade/categoria);
  - duplicatas ("Cuidador de Iguana", "Cuidadora de iguanas", "Iguanas -
    cuidados") fragmentando o catalogo;
  - injecao (XSS/URLs/telefones no nome), homografos (letras cirilicas
    imitando latinas), categorias gigantes para SEO.

DESENHO RECOMENDADO ("criar na hora, publicar na aprovacao"):
  1. A pessoa digita o nicho. Um autocomplete mostra nichos APROVADOS (com
     tolerancia a acento, plural e erro de digitacao) e aliases.
  2. Se ja existe, ela seleciona. Fim. (O "proximo que vier" cai aqui.)
  3. Se nao existe, aparece "Nao encontrei - cadastrar novo nicho". O servidor
     devolve nichos PARECIDOS; se houver similaridade alta, a pessoa precisa
     confirmar que mesmo assim quer um novo.
  4. O nicho nasce com status 'pending', vinculado a candidatura dela.
     So ela (e o admin) o enxerga. Nao aparece para o publico, na busca, no
     sitemap nem em pagina indexavel.
  5. Na triagem da empresa, o admin ve "Nicho proposto: X" com sugestoes de
     similares e decide: APROVAR como novo (pode ajustar o nome), MESCLAR em
     existente (vira alias) ou REPROVAR (empresa escolhe outro).
     A empresa so pode ser aprovada com todos os nichos resolvidos.
  6. Aprovado, o nicho fica publico: o proximo ja o encontra no autocomplete.
     Isso e feito na MESMA triagem que voce ja vai fazer, sem trabalho extra.
  Variante opcional (fase 2): auto-aprovar nichos propostos por donos ja
  aprovados que passem nas validacoes automaticas, com moderacao a posteriori.
  So adotar se o volume de triagem virar gargalo.

4.2 Regras de seguranca e qualidade do nome
  - 3 a 60 caracteres; normalizar Unicode (NFKC); permitir apenas letras
    latinas com acento, numeros, espaco e - & ' . (isso elimina homografos).
  - Rejeitar URLs, e-mails, telefones, repeticao ("aaaa"), so numeros, e
    palavras da lista de bloqueio (palavroes, golpes, marcas proibidas).
  - Chave de unicidade = nome normalizado (sem acento, minusculo, sem
    pontuacao, espacos colapsados). Evita duplicata exata.
  - Similaridade (pg_trgm) >= 0.5 com existente => exigir confirmacao/sugerir.
  - Slug gerado no servidor; palavras reservadas bloqueadas.
  - Limites: 2 propostas por usuario/dia e 5 pendentes por usuario; no maximo
    3 nichos por empresa (evita "category stuffing"); captcha e rate limit por
    IP; teto global de pendentes com alerta ao admin.
  - Somente nichos-folha podem ser criados por usuarios; os GRUPOS de topo
    (Casa, Auto, Pets, Saude...) so o admin cria. O usuario escolhe um grupo
    para o novo nicho (ex.: Pets).
  - Proposta so existe vinculada a uma candidatura/convite valido (nunca
    "orfa"). Pendentes sem empresa por 30 dias sao apagados por job.
  - Concorrencia: dois usuarios propondo o mesmo nicho ao mesmo tempo ->
    INSERT ... ON CONFLICT no nome normalizado; o segundo e apenas vinculado a
    proposta existente.
  - SEO: so entram no sitemap/indexacao nichos aprovados com >= 1 empresa
    aprovada; demais com noindex. Nichos mesclados fazem 301 para o destino.
  - Saida sempre escapada (nunca dangerouslySetInnerHTML com nome de nicho);
    em JSON-LD, escapar "<" como \u003c.

CREATE OR REPLACE FUNCTION suggest_categories(q TEXT, lim INT DEFAULT 8)
RETURNS TABLE (id UUID, name VARCHAR, slug VARCHAR, score REAL)
LANGUAGE sql STABLE AS $$
  WITH n AS (
    SELECT trim(regexp_replace(regexp_replace(lower(unaccent(q)),
           '[^a-z0-9 ]+',' ','g'),'\s+',' ','g')) AS t
  )
  SELECT id, name, slug, MAX(score)::REAL AS score FROM (
    SELECT c.id, c.name, c.slug, similarity(c.normalized_name, n.t) AS score
      FROM categories c, n
     WHERE c.status = 'approved' AND c.is_group = FALSE
       AND (c.normalized_name % n.t OR c.normalized_name LIKE n.t || '%')
    UNION ALL
    SELECT c.id, c.name, c.slug, similarity(a.normalized_alias, n.t)
      FROM category_aliases a
      JOIN categories c ON c.id = a.category_id, n
     WHERE c.status = 'approved'
       AND (a.normalized_alias % n.t OR a.normalized_alias LIKE n.t || '%')
  ) s
  GROUP BY id, name, slug
  ORDER BY score DESC
  LIMIT lim;
$$;

  import re, unicodedata
  NAME_RE = re.compile(r"^[A-Za-z\u00C0-\u00D6\u00D8-\u00F6\u00F8-\u00FF0-9 &'.\-]{3,60}$")
  def clean_name(raw: str) -> str:
      n = unicodedata.normalize("NFKC", raw).strip()
      n = re.sub(r"\s+", " ", n)
      if not NAME_RE.match(n) or n.isdigit() or re.search(r"(.)\1{3,}", n):
          raise ValueError("Nome de nicho invalido")
      return n
  def normalize(n: str) -> str:
      n = unicodedata.normalize("NFKD", n)
      n = "".join(c for c in n if not unicodedata.combining(c)).lower()
      n = re.sub(r"[^a-z0-9 ]+", " ", n)
      return re.sub(r"\s+", " ", n).strip()
